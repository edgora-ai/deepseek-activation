4. 结论：规则是放大器，不是开关

  • 有规则时输出密度更高：Codex 粒子 14000 vs 4500（3×），OpenCode 55000 vs 14000（4×），代码行数 1.2–1.4×。
  • 无规则也出完整黑洞（bloom/吸积盘/星场都在）——质量基线相同，规则不决定成败。
  • DSH 原生（minimal preset）本身就是一种治理：24000 粒子，比两个 CLI 无规则更强；但 opencode+规则（55000）仍超它。
  • 成功率是误导指标：Claude Code 的 "失败" 是假失败（3/3 文件实际写出）；DSH 第二轮超时是 deepseek-free 长输出断流。实际各通道任务都能完成。

7. Claude Code 断流根因分析（最终版）

现象：`claude -p` 复杂任务报 "Execution error"，exit 124（被 timeout 杀），stderr 有 [claude-code:unrecognized_model]（会话标题生成），但文件实际已写出。

实测证据链：

运行stderr文件stdoutEXIT
bh-cc（240s）unrecognized_model✅ 10680 BExecution error124
bh-cc3（300s）unrecognized_model✅ 13452 BExecution error124
bh-cc5（900s 后台）unrecognized_model✅ 11175 B（08:50 写出）空（进程 11+ 分钟未退）—（被 kill）
bh-cc7 claude-sonnet-5*unrecognized_model✅ 10117 B完整最终消息✅ 正常 52s

*并非修复：实测 gateway 把 claude-sonnet-5 路由到真正的付费 Claude Sonnet 5（响应体 model 字段验证）——52 秒正常完成是付费模型的能力，不能作为 deepseek-free 的修复。

根因：Claude Code 有会话标题生成步骤（generate_session_title），用主模型名（deepseek-free）调 gateway → 本地判定 unrecognized_model（deepseek-free 不在标题白名单）→ 标题失败后进程卡在收尾不退出 → timeout 杀 → 报 "Execution error"。文件实际已写出。

为什么 opencode / codex / DSH 没有此问题：它们 headless 批处理没有会话标题生成步骤 —— 任务完成即退出。

可接受的实践：判断"任务成功"应检查文件是否写出（存在即成功），而非只看退出码。Claude Code 用 deepseek-free 时：文件写出 + Execution error = 假失败，属正常。

8. 方法论意义

CLI 上用 AGENTS.md 注入规则层（build/fix 分类 + 每步验证 + 失败重试 + 深度思考）≈ DSH 原生 preset 的效果：殊途同归，验证了移植成功。但不"炸裂"、不是必需 —— 收益是输出密度与纪律，不是能力开关。
